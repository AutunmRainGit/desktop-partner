虚拟伙伴项目——Godot 桌面端完善方案

编写日期：2026-11-09
适用项目：desktop-partner
文档性质：开发计划，不代表功能已完成，也不等同于测试报告。

一、目标与范围

核心愿景：让虚拟角色拥有自己的生活，让陪伴随着时间产生意义。

下一版目标：形成一个能稳定常驻桌面、行为自然、成长可感知、经历可保存的虚拟伙伴。

沿用 Godot 4 + GDScript 和现有四层架构，按照“稳定性 → 桌面体验 → 自主行为 → 成长记录”的顺序完善。
本轮不直接开发 Web 平台、账号体系、云同步、AI 对话、社交系统，也不擅自扩大现有等级体系。
Windows 为主要发布目标，同时保证当前 macOS 开发环境可用。两类平台均须实机验证。

二、现有基础与验证边界

1. 生存、成长、睡眠：已有实现和对应测试文件，需要核查边界及剩余产品规则。
2. 时间结算：已有在线和离线结算、整数余数累计、时间回拨保护，需要检查大跨度性能、觅食事件日期和时区处理。
3. 存档：已有字段校验、临时文件及备份替换，需要补齐启动恢复、版本迁移和失败反馈。
4. 桌面窗口：已有透明、无边框、拖动及屏幕比例缩放；置顶目前被调试开关关闭，仍需配置化和实机验证。
5. 动画：已有16组有效动画，部分尚未接入触发逻辑，需要明确打断、循环与退出规则。
6. 操作界面：已有点击和F/S/W快捷键，需要增加菜单、状态面板和设置。
7. 自主行为、成长记录：尚未形成独立模块，属于新增内容。

历史项目记录提到12个测试脚本、367条断言通过，这是历史验证结果。本方案编写时未重新运行测试，不能据此宣称当前版本全部通过。
开发前应重新检查代码、资源、未提交改动及测试结果，避免覆盖已有工作。

三、第一轮：稳定运行与数据可靠性（最高优先级）

目标：保证角色能可靠地持续生活，关闭重启、时间异常和文件异常不会造成静默数据丢失。

主要涉及：
scripts/application/game_manager.gd
scripts/domain/systems/time_system.gd
scripts/domain/systems/sleep_system.gd
scripts/domain/utils/time_utils.gd
scripts/infrastructure/save_manager.gd
scripts/presentation/main.gd
对应单元测试和集成测试。

1. 分离时间结算与磁盘保存。
时间可继续每秒推进；普通变化建议每30秒保存一次。
喂食、获得经验、升级、睡眠切换等重要事件及时保存，正常退出前执行保存。
记录待保存状态；保存成功后清除，失败时保留并适度重试。
异常退出可能丢失少量尚未保存的普通变化，须明确范围并验证恢复后的结算行为。

2. 补齐启动恢复。
区分正式档正常、正式档损坏、正式档缺失但备份有效、备份也不可用等情况。
恢复前完整校验备份。保留损坏存档，不自动覆盖为新角色。
当前备份替换不能等同于完善的崩溃恢复机制，应测试每个中断阶段。
新增字段和版本时提供默认值或明确的迁移过程，兼容现有存档。

3. 保存失败反馈。
界面提供简短的“尚未保存”状态，后台限频重试，避免每秒弹窗或刷日志。
退出保存失败时给出明确反馈，不将失败误报为成功。

4. 时间结算核查。
覆盖跨午夜、睡眠边界、重复结算、时间回拨、电脑休眠恢复及极长离线。
验证一天、一个月、一年的跨度及耗时；普通周期尽量批量计算，避免逐秒模拟。
当前在线觅食使用结算终点日期，应按真实发生时间归属每日经验，或先明确简化规则。
对当前时区偏移和固定86400秒一天的限制制定明确策略，避免宣称已经支持历史夏令时换算。

5. 防止多实例覆盖。
同一份宠物存档同一时间只允许一个写入实例。
第二个实例给出提示或转到已有实例，避免双方保存覆盖。

验收标准：
关闭重启不重复扣除状态或发放经验。
时间回拨不产生负消耗，状态数值保持合法。
重要事件保存成功后可跨重启恢复。
损坏存档和替换失败不会静默创建新角色。
大跨度结算在约定耗时内完成。
同一角色不会被两个实例同时写入。

四、第二轮：桌面操作与轻量界面

目标：让用户通过鼠标完成主要操作，角色保持视觉中心，减少常驻调试信息。

主要涉及：
scripts/presentation/main.gd
scripts/presentation/window_controller.gd
scripts/presentation/interaction_controller.gd
scripts/presentation/pet_controller.gd
scenes/main.tscn
新增菜单、状态面板、设置界面及SettingsManager。

1. 交互规范。
左键点击：角色回应，符合条件时获得每日经验。
左键拖动：移动窗口，释放后不触发点击。
右键点击：打开操作菜单。
悬停：延迟显示简短状态，离开后隐藏；不唤醒角色。
查看详情：展示生命、饱食度、等级、经验、睡眠和已解锁能力。
退出：保存后退出，保存失败给出明确反馈。

2. 右键菜单首版。
喂面包。
睡眠或唤醒。
查看状态。
成长记录。
设置。
退出。

3. 区分互动与经验奖励。
当天经验已获得时，仍允许角色回应点击。
操作结果分别表达“互动是否成功”和“经验是否增加”，避免将每日经验上限表达为互动被拒绝。
睡眠中第一次实际互动仍只唤醒，不同时执行喂食或经验奖励。

4. 设置首版。
尺寸：小、标准、大、自定义比例。
始终置顶开关。
位置记忆与恢复默认位置。
状态文字展示方式。
自主活动开关。
专注模式。

5. 缩放与位置。
保留屏幕比例缩放，同时允许用户覆盖默认尺寸。
分别管理角色和面板布局，避免文字、菜单随角色放大过度。
跨屏、分辨率变化、显示器断开或恢复位置时，将窗口约束在可见区域。
保持像素美术所需的清晰边缘，并验证不同缩放比例下的实际效果。

6. 透明区域穿透。
按平台能力单独实现和验证，保留关闭入口。
确保角色、菜单、面板区域仍可交互，不以整窗穿透造成无法恢复操作。

验收标准：
不用记快捷键即可完成主要操作。
拖动、点击、菜单互不误触。
尺寸、置顶和位置设置跨重启生效。
调整屏幕后角色仍可找回。
Windows和macOS分别验证透明、置顶、拖动及穿透；未验证平台明确标注。

五、第三轮：自然行为与动画调度

目标：通过现有状态和动画增强生命感，先不新增心情、精力、亲密度等数值。

主要涉及：
新增scripts/presentation/behavior_controller.gd。
完善scripts/presentation/animation_controller.gd。
调整Main的事件连接和动画资源配置。

1. 职责边界。
BehaviorController根据角色状态、空闲时间和用户设置选择可执行的表现行为。
AnimationController作为唯一动画播放入口。
生存、经验、睡眠和觅食规则仍由领域系统管理，表现行为不能直接修改业务数值。

2. 首批行为。
清醒空闲：待机，间隔随机眨眼。
用户点击：挥手或开心回应。
成功喂食：吃面包。
自动觅食成功：吃树叶。
进入和离开睡眠：入睡和醒来动作。
健康偏低或饥饿：对应持续状态动画。
开启自主活动且状态允许：限定范围内短距离行走，作为后续小步交付。

3. 调度模型。
区分持续状态与短暂动作。
每个动作明确允许条件、优先级、持续时间或结束信号、打断规则和冷却时间。
死亡等高优先级状态可打断普通动作。
睡眠不允许普通行走和随机社交动作。
低优先级重复动作合并或丢弃，避免连续点击堆积长队列。
动作结束后根据最新状态回落，不恢复到过期状态。

4. 当前具体问题。
set_state在一次性动作播放期间直接返回，需要补齐高优先级打断。
wave当前为循环动画，不能直接依赖animation_finished回落，应调整循环配置或提供显式结束条件。
行走同样需要停止条件，并同步真实移动；不能只播放行走动画却没有对应位移。
自动入睡、自然醒来等状态变化应具有统一事件来源，避免只在用户操作时播放过渡。

5. 专注模式。
暂停随机挥手、行走和主动提示。
保留生命结算、正常保存及用户主动交互。
主动行为限频，不通过频繁弹窗表达状态。

验收标准：
睡眠不走路，死亡不继续进食或挥手。
连续点击不会卡住动画或形成过长队列。
行走可停止且不越出允许区域。
动作结束后回到正确状态。
专注模式不会暂停角色生活或数据保存。

六、第四轮：成长反馈与经历保存

目标：让成长成为可感知、可回顾的长期经历。

主要涉及：
新增轻量PetEvent数据结构和事件记录模块。
完善GameManager的业务结果和事件输出。
新增成长记录界面及离线摘要。
扩展SaveManager及存档兼容处理。

1. 保持现有等级规则。
先保持一级到二级、二级解锁自动觅食。
满级后继续积累经验，沿用此前用户明确要求。
展示经验进度、已解锁能力和每日经验状态。

2. 明确成长反馈。
升级时提示“已学会自动觅食”。
首次自动觅食成功时记录成长事件。
已解锁能力能在状态面板中查看。

3. 事件记录范围。
出生。
每日经验获得。
升级。
首次自动觅食。
睡眠与唤醒。
重要状态变化。
不记录每一秒消耗，也不无限记录重复点击。
明确事件数量或归档上限，避免存档无限增长。

4. 离线摘要。
重启后展示可关闭的离线摘要，例如离开时间、睡眠时长和状态变化。
离线采用简化觅食保护时，如实说明保护结算，不虚构逐次觅食次数和具体经历。
不因一次重启重复生成同一条重要成长记录。

5. 存储策略。
初版可将数量受限的事件和状态一起保存，减少两份文件写入导致的不一致。
数据量增加后再考虑独立事件文件或数据库，不提前引入复杂存储。

验收标准：
成长和能力变化能够直接看懂。
事件记录跨重启保留且不重复。
离线摘要与真实结算结果一致。
旧存档可通过兼容默认值或迁移继续使用。

七、架构边界

继续沿用Presentation、Application、Domain、Infrastructure四层。

GameManager：组织业务流程，返回状态变化和业务事件，不直接播放动画。
BehaviorController：选择表现行为，不复制生存和成长规则。
AnimationController：统一播放、打断、结束与回落。
SettingsManager：管理窗口、显示及专注模式偏好，与角色生命状态区分。
UI组件：展示信息、提交用户操作，不直接修改PetState。
SaveManager：保存、校验、恢复、版本兼容。
WindowController：窗口及输入控制；平台差异增多后再按实际需要抽出平台适配。

先通过明确的数据对象或业务结果字段传递事件，不立即引入全局事件总线。
所有领域系统继续共享同一个PetState，CharacterConfig运行时只读。
未来引入AI时仅通过受控业务入口提交意图，不直接写生命值、经验和等级。

八、第五轮：发布与运行质量

整理独立运行的导出包及必要说明。
核查MCP开发插件和运行时探针的导出依赖，使产品启动不依赖开发服务。
验证无Godot编辑器环境下的启动、保存及正常退出。
减少高频诊断日志，保留必要错误记录，避免日志无限增长。
检查空闲运行资源占用、长时间运行和电脑休眠恢复。
提供可恢复的窗口位置和清晰的退出方式。
Windows和macOS分别记录已验证的功能与限制。

九、实施顺序

里程碑1：稳定性。
交付：保存频率调整、存档恢复、时间结算边界、多实例保护。
验证：现有测试回归，加故障恢复和长跨度专项测试。

里程碑2：桌面操作。
交付：菜单、状态面板、设置、位置记忆、缩放与窗口可见性。
验证：macOS实测，Windows发布前实测。

里程碑3：行为表现。
交付：先眨眼、点击回应、动作调度，再加入限定范围行走。
验证：连续操作、状态切换、动画打断、专注模式。

里程碑4：成长经历。
交付：能力说明、成长记录、离线摘要。
验证：跨重启保留、事件去重、旧档兼容。

里程碑5：发布整理。
交付：可独立运行的导出包和操作说明。
验证：无编辑器启动、长时间运行及平台检查。

建议先完成里程碑1和2，再接入已有的眨眼、挥手及开心动画，形成第一个完整验收版本。

十、需要在相关开发前确认的产品规则

1. 死亡后如何处理：维持死亡、用户主动重新开始，还是其他方案。
未经确认不实现自动重置、自动复活或覆盖旧角色。

2. 健康如何恢复：现有面包只恢复饱食度，是否新增休息恢复或特定道具，需要明确。
未经确认不改变现有数值规则。

3. 睡眠中是否允许自动觅食：需明确保护机制、业务事件和动画表现之间的关系。
不能只为动画方便擅自改变生存保护。

4. 大跨度在线恢复时，觅食事件与每日经验采用真实事件时间还是明确简化规则。

5. 时区切换和夏令时的首版支持范围，应在发布说明中明确。

十一、开发执行约束

每次任务先检查现有实现，明确目标、涉及文件、方法、依赖、兼容性、验收与测试方式。
保持改动范围可控，不覆盖未提交工作，不做无关重构。
涉及业务规则和存档格式变化时，同步检查调用方、动画、UI及测试。
代码完成后进行语法、相关测试和必要的实机验证，说明未验证部分。
不擅自删除文件或自动git commit。

所有新增功能都应回答：是否增强生命感、是否让互动更有意义、是否产生长期价值、是否符合现有规则、是否增加用户负担、是否适合当前阶段、是否有更简单可靠的实现方式。
